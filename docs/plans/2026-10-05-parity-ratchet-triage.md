# Parity ratchets, classified (2026-10-05)

This covers every item in the three parity-ratchet baselines as of main at bc9c7b1c, 253 in all:
- `tools/retail_hooks_baseline.txt`: 55 callbacks retail Lua defines that the engine never makes.
- `tools/lua_stub_baseline.txt`: 79 bindings that do nothing.
- `tools/blueprint_fields_baseline.txt`: 119 fields set in retail blueprints that only the exe reads and `src/` never names.

For each item the tables give:
- how often retail and FAF use it;
- what Moho does with it, per faf-re;
- what OpenSupCom does today;
- the player-visible effect;
- a severity;
- a one-line fix with a rough size.

Severity scale:
- **HIGH**: changes gameplay outcome, AI behaviour, unit physics/motion, or a commonly used UI interaction.
- **MEDIUM**: noticeable but cosmetic, or uncommon.
- **LOW**: debug, editor, logging, Steam, dead code, or retail never really uses it.

Retail decides the severity. An item goes up one level only when FAF depends on it for a core feature, and the row says so.

Sources:
- Retail Lua and blueprints: extracted from the Steam FA `gamedata/*.scd` (see the extraction-order trap below).
- FAF game Lua: `~/.cache/osc-faf/fa-deploy-faf`.
- faf-re: Draiget/faf-re on GitHub; paths below are relative to its `src/sdk/moho`.
- The engine: `src/` at that commit; line numbers below are from it.

**Traps in the evidence:**
- **Extraction order.** `mohodata.scd` ships 3.7 KB base versions of `lua/sim/Unit.lua`, `Prop.lua`, `Projectile.lua` and `SimUtils.lua`. If it is unzipped after `lua.scd` it overwrites FA's real files, and FA's Unit.lua is 3715 lines. Retail mounts `lua.scd` first, so FA's files win. All counts here use FA's files.
- **The shell's `grep` skips files.** It is a ugrep wrapper run with `-I`, which silently skips ISO-8859 files, and many retail `.lua`/`.bp` files are ISO-8859. Use `command grep -a` or Python.
- **faf-re decompiles FAF's patched exe.** A few behaviours exist only there (SetCommandSource, SetCustomRender, the sim-lane SessionIsReplay) or only in retail's exe (flier ground collision, GroundCollisionOffset). The rows flag these.

## After PR 0 (ratchet hygiene)

PR 0 took the LOW items that are not gaps off the baselines, so each baseline now counts work left to do:
- **Lua stubs, 79 → 50.** 13 registrations were deleted: no retail, FAF or test Lua calls them, and none is a Moho binding (RemoveEnergyDependingEntity, SuspendSim, BeginLogging, EndLogging, CreatePropInSimCallback, GetFrustumTick, OccupyGround, the camera's Lock, Unlock and SyncPlayableRect, the economy event's Destroy, and the sim state's SessionIsMultiplayer and GpgNetSend). 16 moved to `tools/lua_stub_accepted.txt`, each with its reason: 7 correct no-ops and 9 fallbacks or shims for functions the scripts define themselves.
- **Retail hooks, 55 → 49.** `check_retail_hooks.py --extract` no longer lists a module function as a method too. That drops the 6 duplicates here, and 7 more from `retail_hooks.txt` that the engine already makes.
- **Blueprint fields, 119 → 114.** The extract counts `PlayUnitSound('X')` (and the ambient pair) as a read of `Audio.X`, which drops Killed and Spawn (and Load from `blueprint_fields.txt`). DevStatus, LAYER_Orbit and Orbit moved to `tools/blueprint_fields_accepted.txt`.

Where PR 0 departs from the tables below:
- The 8 registrations shadowed by Lua, and SetIgnoreArmyCap, were marked for deletion. They stay as accepted fallbacks: a brain, unit or platoon class without the script's own version would otherwise make a nil call, and retail's own `AIBrain.IgnoreArmyUnitCap` calls SetIgnoreArmyCap.
- The sim state's GpgNetSend was marked as a correct no-op. It is deleted instead, since only UI Lua calls it.

### Notes
- The engine generates no `ButtonDClick` event anywhere, so this is wider than OnDoubleClick. It also breaks the
  Lua `event.Type == 'ButtonDClick'` branches in 15 retail files. Avatars (double-click the ACU/engineer avatar to
  select all and zoom) and filepicker lose behaviour. Button/checkbox/control groups treat a DClick like a press,
  and the engine already sends the second press as ButtonPress, so they still work.
- OnPostLoad matters only on the snapshot-restore path. A save that catches up by replaying orders re-runs the
  scripts and does not need it.
- OnConsumptionActive/InActive on retail is mostly redundant: the toggle path calls SetProductionActive directly.
  FAF moved adjacency-buff application into these callbacks (MassCollectionUnit.lua:20, StructureUnit.lua:796), so
  under FAF a mex next to storage never gets its bonus.
- OnTrackUnit/ShowRenameDialog also need their console commands (UI_TrackUnit, UI_ShowRenameDialog), which the
  memory file moho-input-semantics already lists as M217d gaps.

### Notes

- **NotifyUpgrade is mislabelled in the engine.** sim_bindings.cpp:2609 calls it "cosmetic". faf-re shows it is the only mechanism that carries the factory build queue, repeat-build flag, assisting engineers (guards) and the health ratio across an upgrade. Without it, an upgraded damaged mex comes back at full health. The AI also loses the platoon membership of upgraded mexes and factories.
- **Wreck cap: retail only.** FAF removed the `prop:AddBoundedProp(mass)` call, so FAF has no wreck cap. Retail has one: at 1000 wrecks the cheapest, oldest one is destroyed.
- **MetaImpact never runs in retail.** No blueprint sets MetaImpactRadius/Amount. The only direct caller, ShellTankTerran01, belongs to no unit and passes 4 args, which Moho rejects because it needs 5 or 6 (the 5th is a category). The engine's comment calling it "cosmetic" is also inaccurate: it is a physics knockback impulse.
- **12 of the 40 are dead or correct as no-ops.** These are the "Lua-defined in retail" and "Engine-invented names" groups. Deleting them, and whitelisting the 3 lane duplicates, would shrink the baseline by about 15 with no behaviour change.
- **CameraReset needs care.** The minimap WorldView binds "WorldCamera", which is the main renderer camera. A naive CameraReset would reset the player's main camera one frame after the minimap is created.
- **GetCurrentCommandSource returns the wrong value even in SP.** It gives 0 where Moho gives source+1 or nil, while SessionGetLocalCommandSource gives 1. The related OkayToMessWithArmy always returns true (sim_bindings.cpp:2533), and SetCommandSource is a stub (batch B). Both belong in the same PR.

### Notes

- **Five stubs are not Moho bindings at all.** SetupBuildBones, TurnOffPoolAI and ResetSyncTable are defined in retail
  Lua, so the C++ registration is shadowed by the Lua class, or by the SimSync.lua doscript. RemoveEnergyDependingEntity
  and SuspendSim exist in neither faf-re nor FAF's engine docs. Removing these registrations, and their baseline lines,
  loses nothing.
- **The engine's camera stubs are phantoms too.** Lock, Unlock and SyncPlayableRect are not methods on Moho's CameraImpl.
  The `cam:SyncPlayableRect` calls run in the sim, on the Lua SimCamera class (SimCamera.lua:62), and the UI calls the
  global, which the engine implements.
- **Some no-ops match Moho exactly:**
  - `Trace` (SCR_Trace.cpp:44).
  - All three Histogram methods: Moho's Draw is empty. Retail's `maui/histogram.lua` names a misspelt
    `moho.hostogram_methods`, and nothing imports it.
  - `UpdateSteamLobby`, which is correct offline.
- **SessionIsMultiplayer and SessionIsReplay are only stubbed in the sim state.** The UI-state bindings, where every
  retail caller is, are real (moho_bindings.cpp:4786, app/ui_globals.cpp:281). Retail's exe has no sim-lane form of
  either. FAF's patched exe adds a sim-lane SessionIsReplay, used only by FAF's `lua/sim/score.lua:288`.
- **SetIgnoreArmyCap is dead in retail.** Its only caller is `brain:IgnoreArmyUnitCap`, which no retail Lua or shipped
  map calls, and real Moho has no such global.
- **A related gap sits outside this batch: the unit cap.** The engine caps only build orders, and its test is
  `total >= cap` (unit_orders.cpp:82). Moho checks `total + CapCost > cap` in `Sim::CreateUnit` (Sim.cpp:8132), which
  also covers scripted spawns. On top of that, ChangeUnitArmy is uncapped, and `OnUnitCapLimitReached` and
  `OnFailedUnitTransfer` never fire. SetIgnoreArmyUnitCap only matters once those gates exist; the 22 retail callers
  toggle it around scripted spawns.
- **SpecFootprints never runs at all.** The engine loads blueprints through `/lua/system/Blueprints.lua` and never runs
  RuleInit.lua, so footprints.lua's `SpecFootprints { ... }` is never called. The HIGH gap is the missing
  footprint-class pathing, not the binding body.
- **SetCommandSource and SetCustomRender are FAF binary-patch additions** (SetCommandSource at `.exxt` 0x0128BB51). No
  retail Lua calls either, which is why both are MEDIUM rather than HIGH.
- **The raw grep counts for WorldMesh SetColor and SetScale are inflated by other classes.** Text, Entity and Decal also
  have these methods. On WorldMesh itself, SetColor has 0 callers and SetScale has 1 (FAF only).

# Part 3. Blueprint fields (tools/blueprint_fields_baseline.txt, 119)

## Blueprint fields: air flight model

Scope: 34 fields from `tools/blueprint_fields_baseline.txt` (set in retail .bp files, named in the exe, read by no
retail Lua, never named in `src/`). Unit counts are retail `units/*/*_unit.bp` files (the raw counts add
`mods/CampaignBranch/all_units.bp`); FAF counts from `S/val/raw/bpfields.txt`. faf-re paths are relative to
`fafre_clone/src/sdk/moho`.

What the engine does today, for every row below: all aircraft share one kinematic model,
`Navigator::update_air` (`src/sim/navigator.cpp:408`). It caps yaw at Air.TurnSpeed (1.5 rad/s fallback), banks by a
hard-coded `clamp(0.5 x yaw rate, +-0.5 rad)` and accelerates at `Air.AccelerateRate`. No Moho blueprint has that
field (it is not in RUnitBlueprintAir), so the rate is always the `MaxAirspeed x 0.5` fallback
(`src/lua/sim_bindings.cpp:998,1010`). Aircraft climb at a constant 5 u/s (`src/sim/unit.hpp:1373`) to
Physics.Elevation. On an attack order a flier flies to its longest weapon range, calls `abort_move`, and then hangs
still in the air (`src/sim/unit_orders.cpp:336-374`). An idle flier also hangs where it stopped. There is no
landing, circling, attack run or break-off.

Moho by contrast: aircraft are rigid bodies (`SPhysBody`) driven by a PD controller (`unit/CUnitMotion.cpp:3401`
ComputeAirControl). Winged aircraft run an air-combat state machine (`:3581` ComputeAirCombatTactics, states
`ai/EAirCombatState.h`); non-winged fliers (gunships, transports, drones) circle their target (`:3266`); and every
flier lands when idle (`:3886`).

### Notes

- **Ordered bombers never drop.** order_attack stops a flier at its longest weapon range. For UEA0103 that is the
  bomb's MaxRadius 40, but `Weapon::can_fire` only releases within BombDropThreshold 3 (`src/sim/weapon.cpp:113`).
  So a bomber given an attack order hovers 40 away and never drops. Bombers only hit things they fly over on
  move/patrol legs.
- **The engine reads `Air.AccelerateRate`, which is not a Moho field.** It is not in RUnitBlueprintAir's reflection
  (`resource/blueprints/RUnitBlueprintNestedTypeInfo.cpp:781-822`) and no retail bp sets it, so every flier's
  acceleration is the invented `MaxAirspeed x 0.5`. KMove/KMoveDamping are the real equivalent.
- **TurnSpeed fallback differs.** Without TurnSpeed (gunships, transports) the engine uses 1.5 rad/s; Moho defaults
  to 1.0. Moho's hover family doesn't steer by TurnSpeed at all: it strafes, with force along the desired velocity,
  not the nose.
- **The attack-run port needs four more fields.** No retail bp sets SustainedTurnThreshold,
  RandomBreakOffDistanceMult, RandomMinChangeCombatStateTime or RandomMaxChangeCombatStateTime, so they are not in
  the checker list. The port still needs their defaults: 10, 1.5, 3, 6 (`resource/blueprints/RUnitBlueprint.cpp:382,409-411`).
- **The break-off multipliers are dead today.** SetBreakOffTriggerMult and SetBreakOffDistanceMult are bound and
  serialised but nothing reads them. No retail or FAF Lua calls them either.
- **Three of the 34 items are not air fields.**
  - AttackAngle is an AI field for ships.
  - TurnFacingRate is a Physics field for hover units.
  - BankingSlope is Physics, read only for RULEUMT_Hover, so its 0.5 on 12 air units, Fatboy and XRL0302 is dead
    data.
- **Gunship circling values mostly match the Moho defaults.** Gunships' radius ratios 0.6/0.9, elevation ratio 0.25
  and CirclingTurnMult 3 all equal Moho's defaults. Porting circling with those defaults gets gunships right; only
  transports and drones depend on reading the fields.
- **HoverOverAttack needs checking against the binary.** faf-re's `(!HoverOverAttack && focus && building...) ||
  hasTarget` grouping makes it irrelevant to attacking, which contradicts its help text.
- **faf-re is FAF's patched executable.** Flier terrain collision is hot-patched out there (`unit/CUnitMotion.cpp`
  CalcMoveAir tail comment), and FAF's build drones rely on that.

### Notes

- **Amphibious layer model is wrong in general, not just the offset.** `Unit::is_amphibious()` covers both RULEUMT_Amphibious and AmphibiousFloating. Both switch to "Water" at terrain < water (`src/sim/unit.cpp:552-560`), and ground Y is always max(terrain, water) (`src/map/terrain.cpp:16`). So ACUs, SCUs and amphibious experimentals float on the surface, report layer "Water" to OnLayerChange and never get Seabed. Retail Unit.lua's WaterVision switch keys on Land↔Seabed. Hover units stay "Land" on water. Moho sends Land/Amphibious to Seabed and Hover/AmphFloating (engineers, Salem) to Water.
- **LAYER_* is a real gap, not a false positive.** The keys sit only in Physics.BuildOnLayerCaps. The engine reads that table by literal key and names only LAYER_Land/Water/Seabed (`aibrain.cpp:1165-1167`), so it drops LAYER_Sub: the Cybran HARMS (XRB2308, BuildOnLayerCaps = Sub only) is unbuildable. The UI ghost goes through the same `can_build_structure` (`src/app/window.cpp:125`).
- **"Orbit" is a checker false positive.** It appears only in the unselectable CampaignBranch mod, as a FireTargetLayerCapsTable key. The engine reads that table by the unit's current layer name (`weapon.cpp:547`), so the key would be read if a unit were ever on Orbit. None is. `parse_layer_caps` also ignores an "Orbit" token (`src/sim/weapon.hpp:213`), which is harmless.
- **MaxGroundVariation:** the gap comes from the default, not the 15 set values. Every structure without it uses 1.0 (`RUnitBlueprint.cpp:430`), and FlattenSkirt structures test the skirt edge against the ceiling of a sample height. faf-re's header comment explains a pivot bug it fixed (`sim/STIMap.cpp:3480-3493`); copy its final version.
- **MaxSlope/MinWaterDepth also come from footprints.lua** (SpecFootprints: Vehicle/Amphibious MaxSlope 0.75, water footprints MinWaterDepth 1.5). The engine stubs SpecFootprints (`src/lua/blueprint_bindings.cpp:197`, `src/lua/sim_bindings.cpp:6111`). The engine's fixed slope of 0.75 per 2-unit cell roughly matches the Vehicle footprints. Naval units path by draft = |Physics.Elevation| instead of MinWaterDepth.
- **GroundCollisionOffset:** faf-re is FAF's patched exe. HandleGroundCollision runs only in the GPG retail build, and FAF scripts depend on it being gone (Cybran drones crash it; `unit/CUnitMotion.cpp:4291-4316`). The engine's "fliers never touch terrain" matches FAF.
- **Hover wobble draws on the sim RNG:** CalcMoveHover rolls RandomInRange every 5th tick for every hover unit, even when WobbleFactor is 0 (`unit/CUnitMotion.cpp:1961`). That matters only if the engine ever aims for retail RNG-stream parity.
- **CatchUpAcc and RotateBodyWhileMoving** have no reader in faf-re beyond reflection and the derived default. faf-re is a partial recovery, so treat them as unverified rather than dead.
- **StraddleWater** is a mesh-blueprint field (RMeshBlueprint), not a unit field. In retail it is only on effect meshes and two env props.

### Notes

- **Two fields the engine already honours for every weapon.** UseFiringSolutionInsteadOfAimBone and IgnoreIfDisabled describe behaviour the engine already applies to all weapons (shots fly along the computed solution; disabled weapons are ignored). The divergence is in the unflagged weapons: Moho launches those along the muzzle bone and counts them for range even when disabled. Naming the two flags only matters once that converse behaviour is added.
- **ReTargetOnMiss may do nothing in retail.** The faf-re impact listener (`unit/tasks/CAcquireTargetTask.cpp:701`) returns early unless the weapon has AutoInitiateAttackCommand, and no retail ReTargetOnMiss weapon has it. Read as decompiled, ReTargetOnMiss is therefore inert in retail. The same file once confused the 0x4C and 0x123 offsets (`ai/CAiAttackerImpl.cpp:381`), so check that gate before implementing.
- **Torrent (XAS0306) probably never fires its main weapon.** SetFiringArc (retail weapon.lua:139) gets pitch min = max = 55°. `AimManipulator::tick` then finds a normal-elevation target unreachable, `on_target()` stays false, and `can_fire` blocks. One unit is affected, but it loses its whole main armament. A quick in-engine check is worth doing.
- **Retail bombers fire with MuzzleVelocity = 0.** UEA0103, UAA0103, URA0103, XSA0103 and UEA0304 all have it, so the engine's bomb launch vector is zero and bombs fall straight down. Moho moves them only through RealisticOrdinance (the bomber's velocity).
- **Nukes and shields are already handled; units are not.** Retail `lua/shield.lua:228` lets STRATEGIC MISSILE through shields, so in the engine a nuke still passes a shield. Retail `Unit.lua:972` has no such exemption, so enemy units on the path (air cover above the target, tall units) catch the nuke unless CollideEntity is honoured.
- **Direction and position spreads are filled in but unused.** `src/blueprints/blueprint_store.cpp:263-292` fills in the *Range spread defaults (DirectionXRange 1.5 and so on), but nothing consumes them. DirectionX/Y/Z, PositionY and InitialSpeedRange only take effect when CreateProjectile and CreateProjectileAtBone stop ignoring them.
- **Shared code path with AttackAngle.** SlavedToBody and AI.AttackAngle (in the baseline, not this part) share `unit/CUnitMotion.cpp:2746-2810`. The broadside facing uses the slaved weapon's target, so both belong in one PR.
- **Attack-ground order is missing.** CannotAttackGround depends on attack-ground orders, which the engine lacks: `src/sim/unit_orders.cpp:339` drops an Attack that has no target entity.

### Notes

- **Checker false positives.** Killed and Spawn are Audio cue keys that retail Lua indexes dynamically (`bp.Audio[sound]` in PlayUnitSound). They only matched because "Killed" and "Spawn" happen to appear as words in the exe. The engine already plays them.
- **The picking gap is bigger than the five fields.** The engine projects the cursor onto the terrain and tests footprints (input_handler.cpp:243, :694). Moho tests the cursor against the mesh's world AABB, trimmed or scaled by the selection fields, and uses an OBB ray test below UseOOBTestZoom. Until the picker uses height, flying units at close zoom (camera pitch near 40°) can only be clicked where the ground behind them falls under the cursor.
- **Sacrifice formula.** `order_sacrifice` reads `build_cost_mass_`, which holds the cost of whatever that unit is building. Both the sacrificer's and the target's values are usually 0, so an Aeon sacrifice adds about 0 progress before the engineer dies. Moho uses the sacrificer's own BuildCostMass/Energy × the multipliers, and takes the smaller of the mass and energy fractions of the target's cost.
- **InitialAutoMode and GuardScanRadius also feed CUnitPodAssist**, which the engine does not have. That task makes UEF ACU/SACU drones and Kennel/Hive pods auto-repair and assist inside GuardScanRadius while in auto mode. FAF also sets silo auto mode from preferences (StructureUnit.lua:895); that path is FAF-only.
- **StrategicIconSize on units is dead.** The 3 drone unit blueprints set it at the top level, but Moho reflects the field only on RProjectileBlueprint.Display.
- **RebuildBonusIds pays out in retail.** *Corrected (2026-10-08):* Moho runs `GetRebuildBonus` on the builder (Unit.lua: 0.5), not on the prop, so a structure rebuilt on its own wreck starts half built; FAF's Unit.lua returns 0 and pays its bonus from OnStartBuild instead.
- **Attack-move (IssueAggressiveMove, IssueFormAggressiveMove) is a plain move in the engine.** Moho's patrol and guard tasks run the same FindBestEnemy scan with GuardScanRadius, so the scan code should be shared with any attack-move work.
- **Lifebar visibility rules differ too.** Retail draws bars on all friendly units within ui_LifebarLOD, and on enemies only when hovered or forced (CWldSession.cpp:14679-14697). The engine draws them on any visible unit, but only when damaged or selected.
