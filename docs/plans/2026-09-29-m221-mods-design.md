# M221: Mods

## Why

FA's mods are data and Lua. A mod is a folder under `/mods` with a
`mod_info.lua`; what it changes, it changes through three engine rules:

- **hooks:** after the engine runs a script, it runs every active mod's
  `<mod><hookdir><script path>` too, in the same environment, so a hook
  extends the script's functions and classes rather than replacing the file;
- **blueprints:** `Blueprints.lua` loads every `.bp` file in each active
  mod's folder, then calls `ModBlueprints`, which mods hook to change any
  blueprint;
- **the game's mod list:** the lobby's `Mods.GetGameMods` picks the mods a
  game uses, the launch carries them to the sim, and the sim's and the
  session UI's `__active_mods` are that list.

Retail ships five such mods in `gamedata/mods.scd` (Chess, Nothing But
Time, Resource Rich, Retirement, the campaign branch), and retail's
`mods.lua` is the mod manager's model. What the engine lacks:

- `doscript` runs a script's hooks as separate chunks, only from the init
  file's hook directories (`/schook`). A hook can't see the file's locals,
  and no mod's hook runs.
- `__active_mods` is always empty: in the sim, in the game's UI, and in
  replays.
- The game's UI state runs `userInit.lua` where Moho runs
  `SessionInit.lua`, which is where UI-only mods join the session.

The rules come from faf-re (`CScrLuaObjectFactory.cpp`: `func_LuaDoScript`,
`SCR_LuaDoFileConcat`; `RRuleGameRules.cpp`; `CWldSessionLoaderImpl.cpp`;
`SessionStartup.cpp`; `CLobby.cpp`) and the retail scripts (`mods.lua`,
`SessionInit.lua`, `Blueprints.lua`, `lobby.lua`, `SinglePlayerLaunch.lua`).

## The rules

### doscript
- `doscript(path, env)` builds a list of files:
  1. the script itself (an error if it isn't found);
  2. for each init-file hook directory (`hook = {'/schook'}`), in order,
     `<dir><path>` if it exists;
  3. for each entry of the calling state's `__active_mods` (index 1, 2, ...
     until nil), `<location><hookdir or '/hook'><path>` if it exists. An
     entry without a `location` is skipped; an empty `hookdir` is `/hook`.
     Moho logs `Hooked <path> with <hook>` for each.
- The files are **one chunk**, named `@<path>`: each file's bytes in turn,
  with a newline between two files when the first doesn't end in one. So a
  hook sees the script's locals, and a script's `return` can't be followed
  by a hook (Moho's rule too).
- The chunk runs in `env` when given. A runtime error propagates to the
  caller of `doscript`.
- *Engine differences kept:* a UTF-8 BOM is stripped from each file (retail
  data has them; Moho's LuaPlus reads them some other way), and a chunk
  that fails to compile is an error where Moho only warns and runs nothing
  (the engine's callers already report it, and a hook with a syntax error
  otherwise makes its script silently absent).

### Where `__active_mods` comes from
- **The launch:** `LaunchGame(gameInfo)` takes `gameInfo.GameMods`, which
  retail's lobby sets to `Mods.GetGameMods(gameInfo.GameMods)` just before:
  a list of the chosen mods' `mod_info` tables, sorted by uid (then
  `before`/`after`). A single-player launch (`LaunchSinglePlayerSession`)
  takes `scenarioMods` instead. Each peer computes its own list from its
  own copy of the mods.
- Moho serializes the list (`SCR_ToString`) into the launch info and the
  replay; the rules' Lua state reads it back (`SCR_FromString`) as its
  `__active_mods` (an empty table when there is none) and then runs
  `RuleInit.lua`, which loads the blueprints.
- The rules copy `__active_mods` and `__blueprints` into the sim's state
  and into the session's UI state (`ExportToLuaState`).
- The session's UI state then runs `/lua/SessionInit.lua`: `userInit.lua`,
  then every UI-only mod the player has selected (`Mods.GetUiMods()`)
  appended to `__active_mods`, then `UserSync.lua`.
- The front end's UI state has no game mods.

### Mods on disk
- Retail's init file mounts each entry of
  `<Documents>/My Games/Gas Powered Games/Supreme Commander Forged Alliance/mods`
  at `/mods/<name>` (`mount_contents`, an archive's extension dropped), and
  `gamedata/mods.scd` at `/`.
- `mods.lua` finds mods with `DiskFindFiles('/mods', '*mod_info.lua')`, runs
  each `mod_info.lua` in a table of defaults (`hookdir = '/hook'`,
  `selectable = true`, `uid` the file name) and sets its `location` to the
  folder. The player's choice is the preference `active_mods` (uid -> true).
- A mod's "shadow" folder is documented in `mods.lua` but Moho doesn't
  implement it.

## The design

### M221a: hooks, Moho's way
`lua::run_vfs_script` builds the file list above and runs it as one chunk.
The mod entries are read with raw gets (an absent `__active_mods`, or one
that isn't a table, means no mods). The list is also exposed (for tests and
logging) as `script_hooks(L, vfs, path)`.

Tests (unit): a hook sees and replaces the script's locals; hooks from the
init directories, then from `__active_mods` in its order; `hookdir` given,
defaulted and empty; entries without a location skipped, and the list
ending at the first nil; a file without a final newline joined to the next;
a BOM in a hook; an error in a hook fails the script; the stack is kept.

### M221b: the game's mods
- `sim::GameSetup` gets `mods`: the launch's list, serialized as a Lua value
  (`lua::lua_to_bytes`: plain data -- nil, booleans, numbers, strings and
  tables of them -- keys in a fixed order; nesting past 32 levels, and so a
  table inside itself, and more than 16 MiB refused; `push_lua_bytes` reads
  it back and refuses anything but exactly one such value). It is written
  in replays, and so in saved games: replay format version 10.
- The session config reader takes `GameMods` (the lobby's) or, without it,
  `scenarioMods` (single-player).
- `lua::set_active_mods` sets a state's `__active_mods` from those bytes (an
  empty table for none). The reload reads the game's setup **before** it
  loads the blueprints and sets the new sim state's; a headless `--replay`
  or `--load` sets the recorded game's. The bindings that used to set
  `__active_mods = {}` create it only when it is absent.
- The game's UI state: the launch's mods are its `__active_mods` before its
  blueprints load (the engine loads the UI's blueprints itself rather than
  copy the sim's; with the same mods the result is the same). It then runs
  `/lua/SessionInit.lua` (when the data has one) instead of `userInit.lua`,
  so the player's UI-only mods join, and the world UI doesn't load
  `UserSync.lua` again. A `--map` game's state is a game's when its
  interface starts; a headless test mode's bare state stays the front
  end's kind.
- **Mods on disk:** retail's init file already mounts the player's mods at
  `/mods/<name>`, but `DiskFindFiles('/mods', ...)` never saw them: the
  VFS searched only mounts at or above the directory. A mount below it is
  now searched whole (which also brings the player's own maps, at
  `/maps/<name>`, into the lobby's map list).

Tests:
- unit: `lua_bytes` (round trips, a fixed order, what is left out, cycles,
  depth and size -- shared tables doubling at each level -- and malformed
  and truncated bytes); the session config's mods;
  `set_active_mods` on good and bad bytes; the bindings keeping a launch's
  mods; the replay's mods (and none before version 10); `find_files`
  across mounts below the directory;
- data (`data.mods_flow`, `--mods-flow-test`): a temporary Documents
  folder's mods folder holds a game mod (its own `uel0001_unit.bp` merged
  into the ACU's, and hooks of `simInit.lua` and `userInit.lua`) and a
  UI-only mod (hooks of `userInit.lua` and `UserSync.lua`); the
  preferences select both and retail's Resource Rich. A skirmish launched
  from the front end as retail's lobby launches one must give the sim the
  two game mods (sorted by uid), the game's UI those and the UI mod, both
  the ACU with Resource Rich's doubled production and the mod's name, and
  each state the hooks Moho would run there -- not the UI mod's
  `userInit.lua` hook, which runs before UI mods join -- and `UserSync.lua`
  loaded twice (by retail's `SessionInit.lua` and its `/schook` hook), not
  a third time by the world UI. Its recording must replay headless with the
  same mods, checksums matching, and, watched in the game (`--watch`), give
  the same report.

### M221c: the mod manager
- Retail's mod manager dialog (`/lua/ui/dialogs/modmanager.lua`) runs from
  the lobby: listing `/mods`, selecting mods into the `active_mods`
  preference, and the lobby's `GameMods` following it.
- A mod packed as an archive in the player's mods folder (`mount_contents`
  mounts `.scd`/`.zip` too).

Tests: a UI test that opens the dialog, selects a mod and launches with it.

## Not in M221
- FAF's own mod machinery (FAF's `mods.lua`, its `__active_mods` from the
  FAF client's GPGNet `GameMods`): with M220d, FAF's own scripts.
- Mod "shadow" folders (not in Moho).
- The mod vault (downloading mods): FAF's client does that.
